# 他業界の製品リサーチと取り入れる点

- 作成：2026-11-21
- 目的：介護以外の業界で「期限・依頼・提出物の回収・証拠・承認・現場の職員への連絡」を支えている製品を調べ、**シンプルさ・使いやすさ・デザイン**の考え方を本製品に取り入れる
- 方法：公開情報（公式のヘルプ・設計資料を優先、販売ページ・記事は「各社の説明」として区別）。調査日は 2026-11-21。製品の仕様は変わるため、実装前に再確認する
- 取り入れ方の原則：**考え方と一般的なパターンを取り入れ、他社の画面・ブランド・文言をそのまま写さない**（最初の指示書の禁止事項）。デジタル庁デザインシステムは公開・再利用を前提とした資料のため、利用条件（第4章）に従って基礎に採用する
- 反映先：`design-guidelines.md`（新規）、`screen-design.md`、`module-specifications.md`、`development/technical-decisions.md`（TD-070〜TD-077）

| Microsoft Teams（タスクの配信・承認） | 小売など現場の多い企業 | 本部から各拠点への業務配信、承認 | 一斉配信と拠点別の完了率、チャットの通知から承認 |

## 2. 製品ごとの学び

### 2.1 Google Classroom（学校の課題回収）

| 事実（出典） | 取り入れ方 |
|---|---|
| 先生は課題ごとに生徒の状況を一覧で見られ、「提出済み」「割り当て済み」「採点済み」などで並べ替えできる | **提出状況表（A09）**を「1人1行・状態で並べ替え・絞り込み」にする |
| 採点簿では、期限切れの未提出が赤、提出済みが緑、返却済みが黒で表示される | 色に加えて文字とアイコンで示す（色だけに頼らない）。赤は「期限超過」だけに使う |
| 複数の生徒の提出物をまとめて返却できる。返却された課題には、コメントへの返信や再提出ができる | **一括承認**（同じ依頼の提出物をまとめて承認）、差し戻し後の再提出の流れを1つにする |
| 期限までに提出されなかったものは自動で「未提出」と表示される | 期限を過ぎた未提出は自動で「未提出（期限超過）」と表示（すでに設計済みの算出を表示に反映） |

### 2.2 LINE WORKS（業務連絡の既読・再通知）

| 事実（出典） | 取り入れ方 |
|---|---|
| 掲示板の投稿では、投稿者と管理者が既読メンバー・未読メンバーを一覧で確認できる | 委員会の結果の周知（D-7）を採る場合、**既読・未読の一覧**を同じ形にする。日本の職員にとって「既読」は慣れた考え方 |
| 未読メンバー全員、または選んだ相手にだけ再通知できる | 督促は「未提出の人だけ」「選んだ人だけ」に送る（設計済み）。送る前に人数を表示 |
| 導入企業の声として、誰が既読か分かるため未読者にだけリマインドできた | 「全員に何度も送る」をやめ、必要な人だけに届ける方針を確認 |

### 2.3 SmartHR（年末調整の質問形式・デザインシステム）

| 事実（出典） | 取り入れ方 |
|---|---|
| 年末調整は、従業員が「はい」「いいえ」で答えていく質問形式。分かりにくい言葉には説明が出る（2016年の発表記事） | 職員の入力（提出・完了報告・初回登録）は**質問に1つずつ答える形**にする。専門用語には短い説明を付ける |
| 利用者の声として「QRコードから入るのが一番分かりやすかった」 | 招待・初回登録で**QRコード**を使えるようにする（D-2 の候補に反映） |
| デザイン原則に「ユーザーの時間は有限だ」「言葉からはじまるデザイン」 | 本製品の原則にも「言葉をそろえる」を入れ、用語集と状態の表示名を1つに決める |
| 文章のチェックリスト：常用漢字、一文50文字程度、主語・助詞を省かない、二重否定を避ける、「！」など過度な強調を避ける、3桁以上の数字にカンマ、略称は括弧で補足 | `design-guidelines.md` の文章ルールにそのまま採用 |
| エラーメッセージは「事象・原因・対処」の3つを含め、場所が足りなければ「原因＞対処＞事象」の順に優先 | エラー文の型に採用 |
| ワンクッション（確認）が必要なのは取り返しのつかない操作。確認には「対象の件数と、実行すると何が起きるか」を表示する | 確認ダイアログは**削除・一括操作・多数への送信**だけに出し、件数と結果を書く |
| 値がない項目は空白、入力できない項目は「-」 | 一覧の空欄の扱いに採用 |
| アクセシビリティ：文字のコントラスト比4.5:1以上、200%拡大で利用可能、同じ情報の再入力をさせない、重要な通知は操作の近くに出す | 基準に採用 |

### 2.4 Microsoft Teams（本部からの業務配信・承認）

| 事実（出典） | 取り入れ方 |
|---|---|
| 本部がタスクの一覧を作り、組織の階層やファイルで指定した拠点に一斉に配信できる。受け取った側はタイトルや内容を変更・削除できない | **PHASE 7（法人本部）**の設計方針：法人共通の業務を施設に配信し、施設側では内容を変更できないようにする |
| チェックリストや承認などの完了条件を満たさないと完了にできない | 「必要提出物がそろわないと完了報告できない」（設計済み）と同じ考え方であることを確認 |
| 配信後、拠点・一覧・タスク別に完了状況を確認できる | 法人ダッシュボード（PHASE 7）は「施設別の完了率→施設→業務」とたどれる形にする |
| 承認はチャットに届くカードから内容を見て承認・却下でき、結果がカードに反映される | **通知一覧・承認待ち一覧から、その場で承認・差し戻し**できるようにする（画面を行き来させない） |

### 2.5 Crunchtime Ops Execution（旧 Zenput、外食チェーンの店舗業務）

| 事実（出典。販売ページ中心） | 取り入れ方 |
|---|---|
| 全店舗で業務が行われたかを確かめ、店舗・地区・全体の単位で報告を見られる | 法人ダッシュボード（PHASE 7）の階層の参考 |
| チェックで不備（写真のない清掃項目など）があると、地区の責任者に通知し、店長に別の対応業務を自動で割り当てる | 委員会の決定事項から改善業務を作る（設計済み）に加え、**「不備 → 対応業務と上長への通知」**を将来の点検機能の型にする |

### 2.6 SafetyCulture（定期点検と是正）

| 事実（出典） | 取り入れ方 |
|---|---|
| 点検の予定は、ひな形・場所・担当・間隔・頻度で作り、期限後の提出を認めるか選べる | 年間業務の繰り返し設定と「期限後の提出を認めるか」（設計済み）を確認 |
| 点検中や報告の確認中に、担当・期限・優先度付きの対応（是正）を作れる。アカウントのない人にも割り当てられる | 委員会の開催記録の画面から**その場で改善業務を作る**導線にする。アカウントのない職員は代理登録・印刷（設計済み）で対応 |

### 2.7 Drata（監査の証拠と定期業務）

| 事実（出典） | 取り入れ方 |
|---|---|
| 業務に担当・期限・繰り返し（週・月・四半期・年・任意）と終了時点を設定できる | 本製品の繰り返し設定（設計済み）と同じ。終了時点の指定を画面に出す |
| 証拠に有効期限・見直し日があり、その日が来ると担当者に自動で業務が割り当てられる | **書類の「見直し日」**（指針・マニュアル・BCP などの定期見直し）から見直しの業務を自動で作る（PHASE 3 の候補） |
| 期限までに終わらない業務は解決するまで「期限超過」と表示され、期限が近いもの・超過したものを週1回などのメールでまとめて知らせる | 管理職向けに**週1回のまとめメール**（今週の期限・超過・承認待ち）を設ける |
| 業務を月ごとの時間軸で、種類ごとにまとめて表示する | 管理者のカレンダーの年・月表示を「月×カテゴリ」でまとめる（設計済みの年表示を強化） |

### 2.8 Content Snare（書類の回収と督促）

| 事実（出典。各社の説明を含む） | 取り入れ方 |
|---|---|
| 督促の予定に「既定」「自動の督促なし（最初の連絡だけ）」「自分で作った予定」を選べる | 提出依頼ごとに**督促の型**を選べるようにする（既定／督促なし／自分で設定） |
| 反応のない相手には、担当者自身に「電話する」リマインドを送れる | 督促を一定回数送っても未提出の人がいる場合、**依頼者に「直接声をかけてください」**と知らせる（アカウントのない職員・通知を見ない職員への対策） |
| 督促にかかる時間が71%減ったという利用者の報告がある（各社の自己申告） | 効果の目安としてのみ参照（独立した測定ではない） |

### 2.9 Todoist（今日やること・今後の見通し）

| 事実（出典） | 取り入れ方 |
|---|---|
| 「今日」の画面に、すべてのプロジェクトの今日の予定がまとまる。期限超過も「今日」に表示される | 職員ホームを**「今日のやること」**中心にし、超過は一番上に出す |
| 「今後」の画面は週の移動ができ、予定がある日には小さな点が付く | 職員・管理者の週表示に「予定のある日に印」を付ける |
| 一覧が長すぎると負担なので、重要な3つに絞ることを勧めている | ホームに出す件数を絞り、残りは「すべて見る」へ |

### 2.10 Basecamp（静かな通知）

| 事実（出典。各社の説明） | 取り入れ方 |
|---|---|
| 3つに分かれていた通知の受け口を1つ（Hey! メニュー）にまとめた。そこからほぼすべての通知を止められる | **通知の受信箱を1つ**にする（C03）。種類ごとの受信設定はマイページ |
| 個別の通知を減らし、落ち着いて使えるようにすることを意図している | 職員向けの通知は**まとめて送る**（同じ人・同じ時間帯の通知を1通にする） |
| 決まった日時に質問し（例：毎週月曜「今週は何をしますか」）、答えをまとめて見られる | 取り入れない（今は新機能を増やさない）。PHASE 5 以降に月次の振り返りとして検討 |

### 2.11 Connecteam（共用端末）

| 事実（出典） | 取り入れ方 |
|---|---|
| 1台の端末を複数の職員が使い、自分のプロフィールに切り替える専用アプリがある。通常のアプリは個人のスマホ用 | D-2 の「共用タブレット方式」の具体像：職員を選ぶ → 暗証番号 → 操作 → 自動で戻る |
| 共用端末では、一定時間操作がないと自動でログアウトする。ログイン時の自撮りを求める設定もある | 自動ログアウトは採用候補。**自撮り（顔の画像）は取り入れない**（職員の顔画像という個人情報を増やすため） |
| 縦向きのみで横向きに対応していない点に不満の声がある | 共用タブレットは縦・横の両方に対応する |

### 2.12 Notion Q&A（根拠付きの回答）

| 事実（出典） | 取り入れ方 |
|---|---|
| 回答に、参照したページ（文書内の該当箇所）を示す | AI の回答の下に**根拠のカード**（業務・書類・提出状況へのリンク）を必ず表示（設計済み） |
| 質問した人が閲覧できるページだけを使って答える | 質問者の権限で検索する（設計済み）ことを確認 |
| 登録されていない話題には答えを返さない | 「登録情報からは確認できません」の定型表示（設計済み）を確認 |

### 2.13 GOV.UK Design System（慣れない人が使う手続き）

| 事実（出典） | 取り入れ方 |
|---|---|
| フォームは「1画面に1つのこと（1つの情報・1つの判断・1つの質問）」から始める。理由：何を求められているか分かる、集中できる、スマホで使いやすい、間違いから戻りやすい | 職員の操作（提出、完了報告、初回登録）を**1画面1つ**にする。管理者の画面は調査で必要と分かれば1画面にまとめてよい |
| 複数の作業を何回かに分けて進める手続きでは「作業一覧」を使う。状態は「完了」「未完了」から最小限で始め、必要なら「未着手」「作業中」「まだ始められない」を使う。「完了」は色なしの文字、注意が必要な状態だけ色付きのラベル、赤はエラーにだけ使う | **初期設定**（はじめての設定）と**年度更新**を作業一覧の形にする。状態の表示名は少なく保ち、完了は静かに、赤は期限超過とエラーだけ |
| 進み具合の表示はまず付けずに試す | 職員の3段階の提出では進み具合の表示を付けず、調査で必要なら追加 |
| 必須の項目に「＊」だけを付けない。任意の項目に「（任意）」を付ける | 日本の行政の基準（デジタル庁：「※必須」「※任意」の文字）に合わせる |

### 2.14 デジタル庁デザインシステム（日本語の画面の基準）

| 事実（出典） | 取り入れ方 |
|---|---|
| 本文・UI の文字は16px 以上が基準。14px は基本的に使わず、14px 未満は原則認めない。本文の行の高さは1.5倍以上（本文は150〜175%）。日本語の斜体は避ける。フォントは Noto Sans JP | 文字の基準にそのまま採用 |
| 文字と背景のコントラスト比は文字の大きさに関係なく4.5:1以上、部品・図形は3:1以上。色だけで区別しない | 色の基準に採用（本製品の色は計算で確認済み：`design-guidelines.md` 第2章） |
| フォーカス（キーボードで選ばれている場所）は黄色と黒の二重の表示 | 同じ考え方を採用 |
| ボタンの高さの目安は 56・48・36・28px、押せる範囲は44px 以上。目立つボタン（塗り）は原則1画面に1つ、キャンセルはテキストボタン。無効にする場合は近くに理由や有効になる条件を書く | ボタンの基準に採用 |
| 入力の項目名と補足は縦に積む。「※必須」「※任意」を全角の「※」で書く。補足の代わりに入力欄内の薄い文字（プレースホルダー）を使わない。エラーは具体的な内容と直し方を書く。入力の途中でエラーを出さず、送信時や確認時に知らせる | 入力の基準に採用 |
| 目標は JIS X 8341-3:2016 の適合レベル AA。WCAG 2.2 も参照 | 本製品の目標にする |

## 3. まとめ：取り入れる考え方

調査から、本製品のデザイン原則を次の7つにまとめた（詳細は `design-guidelines.md`）。

| 原則 | 主な出どころ |
|---|---|
| ① 今日やることから始める | Todoist、Google Classroom |
| ② 職員の操作は1画面に1つのこと | GOV.UK、SmartHR（年末調整） |
| ③ 状態は少なく、言葉と色で示す（色だけに頼らない） | GOV.UK、Google Classroom、デジタル庁 |
| ④ 通知は静かに：まとめて、必要な人にだけ | Basecamp、LINE WORKS、Drata |
| ⑤ その場で終わらせる：通知から承認、一覧からまとめて | Microsoft Teams、Google Classroom |
| ⑥ 根拠を見せる：AI の回答、法令の根拠、提出の控え | Notion、Drata |
| ⑦ 確認は取り返しのつかない操作だけ。件数と結果を書く | SmartHR |

## 4. 取り入れないもの

| 他社の機能・考え方 | 取り入れない理由 |
|---|---|
| 今日の一覧を空にするため、期限を気軽に先送りする（Todoist） | 行政提出・委員会などは期限を動かせない。期限の変更は管理者が理由を記録して行う |
| チャットを中心にした画面（LINE WORKS・Teams のトーク） | 記録が流れて探せなくなる。通知の届け先としてのチャット連携は D-1 で検討 |
| 共用端末での自撮りログイン（Connecteam） | 職員の顔画像という個人情報が増える |
| 自動の定期質問（Basecamp） | 新機能を増やさない方針。PHASE 5 以降に検討 |
| ゲームの要素（連続達成の表示など） | 業務の記録に不要で、職員の負担になりうる |
| 進み具合の表示をすべての画面に付ける | 調査で必要と分かってから（GOV.UK の推奨） |
| 他社の配色・画面の構成・文言をそのまま使う | 指示書の禁止事項。公開の基準（デジタル庁）以外は考え方だけを使う |
