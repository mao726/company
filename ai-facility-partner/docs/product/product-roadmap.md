## 1. 指示書のフェーズとの調整（TD-020、承認が必要）

| 指示書 | 問題 | 調整 |
|---|---|---|
| 提出物回収（PHASE 2）は「承認・差し戻し」「期限前の通知」を含むが、承認機能・通知は PHASE 3 | PHASE 2 だけでは提出物回収が完成しない | 1段階の承認とアプリ内通知を PHASE 2 に前倒し。PHASE 3 で多段階承認・メール・通知設定画面を追加 |
| 操作履歴は PHASE 3 | 後から追加すると PHASE 2 期間の記録が残らない | 記録は PHASE 2a から。閲覧画面を PHASE 3 |
| ダッシュボード（PHASE 2）に「委員会・研修予定」「AIからの確認事項」 | 委員会は PHASE 3、AI は PHASE 4 | PHASE 2 は「委員会」「研修」カテゴリの業務を予定として表示。確認事項は「自動チェック（AIではない）」として表示 |
| 権限管理（PHASE 2） | カスタムロールまで作ると重い | PHASE 2 は標準6役割と割当（割当の規則つき）。カスタムロールは PHASE 3 |

## 2. フェーズ別の開始条件・内容・完了条件

完了条件の必須テストは `development/test-strategy.md` 第4章（正本）。

### PHASE 1：基盤設計

- 内容：本設計文書一式、レビュー指摘の修正
- 完了条件：**事業責任者の設計承認**

### PHASE 2a：基盤（目安4週）

- **開始条件**：
  - PHASE 1 の承認
  - 介護SaaS専用リポジトリ（Q1）
  - ホスティング先（Q2）
  - 職員のログイン方式（D-2）と認証サービス（TD-016）
  - コードレビュー担当（Q5）
  - 職員数の数え方（D-5③。契約判定の実装に必要）
- 内容：
  - プロジェクト雛形・CI（DB 構成の検査、ログの個人情報検査を含む）
  - DB・RLS・文脈の設定・ジョブ（DB 待ち行列）
  - 認証・多要素認証・再認証・リクエストごとの状態確認
  - 法人・施設・業態・設定の階層（設定定義表）
  - 職員・所属・ユーザー・招待・即時停止
  - 役割・権限判定・割当の規則
  - 契約判定（プラン・権利・契約）
  - 操作履歴・ログイン履歴・利用記録
  - ファイル基盤（二段階の保管・検査・配信）
  - バックアップの仕組み（時点復元の設定、別アカウントへの日次バックアップとファイル複製、保守用の専用関数の骨格）
  - 支援アクセス
  - 当社の管理画面（法人・施設の作成、施設長の招待）
- 完了条件：test-strategy 第4章の「2a」列

### PHASE 2b-1：業務（目安4週）

- **開始条件**：PHASE 2a の完了、**実証施設のヒアリング完了**（Q3）、アプリ外の通知手段（D-1）、併設事業所の扱い（D-4）、標準テンプレートの作成担当（D-9）
- 内容：
  - 業務・状態遷移・承認（1段階）
  - 繰り返し生成・年間業務・テンプレート・年度更新
  - 業務依頼・行政提出の項目
  - ダッシュボード・アプリ内通知・**D-1 で選んだアプリ外の通知手段**
  - 職員・年間業務の CSV 取込
  - 特養の標準テンプレート（D-9）、年間業務の根拠の一括確認（導入直後の「未確認」の警告を減らす）
- 完了条件：「2b-1」列。架空データで業務の一巡

### PHASE 2b-2：提出物・書類（目安4週）

- **開始条件**：PHASE 2b-1 の完了、職員の機密情報の扱い（D-8）
- 内容：
  - 提出物回収（データ区分・代理登録・対象外・印刷）
  - 書類管理（アクセスレベル・データ区分・紐付け・保存期限）
  - カレンダー（月・週・年、年間行事表の印刷）
  - 提出物の通知
  - 施設の利用状況画面（A29。効果測定に使う）
- 完了条件：「2b-2」列。D-3 を採る場合は、テスト10（復元訓練）もこの時点で実施

### 【D-3】早期の限定運用（判断待ち）

PHASE 2b-2 の完了後、PHASE 3 を待たずに、実証施設で**限定した範囲の実運用**を始める案。

- 範囲：業務・依頼・提出物・書類のみ。データ区分は C1〜C2 に限る
- 条件：`architecture/security-design.md` 第9章のうち、次の項目が満たされていること
  - ガイドラインのチェックリストの確認（専門家の確認を含む）（第9章1）
  - 再委託先の整理と専門家の判断、施設向けの公表文・職員向け説明の雛形（同2）
  - 契約とサービス仕様の開示書（同3）
  - 運用体制（同4）
  - その時点までの必須テストの合格（同5）
  - 脆弱性診断（同6）
  - 復元訓練（同7。テスト10を 2b-2 で実施）
  - インフラ統制の実施確認（同8）
- 目的：利用データを見てから PHASE 3 以降の範囲を決める（使われない機能を作らない）

### PHASE 3：管理機能（目安5週）

- **開始条件**：PHASE 2b-2 の完了、法人本部への提供価値（D-6）、運営指導への備え（D-7）。D-3 を採った場合は限定運用の利用データの確認
- 内容：
  - 委員会・研修・要件一覧（未確認の一括確認画面を含む）
  - 多段階承認、メール通知、通知設定画面
  - 操作履歴・ログイン履歴の画面、権限の棚卸し
  - CSV 出力、カスタムロール
  - 完了日ベースの繰り返し
  - 操作履歴のダイジェスト、保存期限ルール
  - 契約・プランの閲覧画面（A22）、当社管理画面の要件候補の管理
- 完了条件：「3」列

### PHASE 4：AI 機能（目安5週）

- **開始条件**：PHASE 3 の完了、AI 事業者と送信範囲（Q4）、外国事業者への提供に関する専門家の判断（E-1）
- 内容：
  - AI 接続層・送信フィルタ
  - 施設運営AI（質問回答）
  - 文書読み取り・分類・抽出、議事録下書き（施設が有効化した場合）
  - 改善提案
  - AI 利用状況・事業者の条件の画面
  - 日本語の本文検索
- 完了条件：「4」列（AI 評価基準を含む）

### 実データ前の準備（PHASE 3〜4 と並行）

- `architecture/security-design.md` 第9章の全項目

### PHASE 5：実証・改善（2〜3か月）

- 内容：実証施設での運用、効果測定（導入前の基準値との比較）、改善
- 開始条件：実データ前の準備の完了
- 完了条件：削減時間の測定結果、継続利用の意思

### PHASE 6・7

- PHASE 6：別途計画。セルフ登録、施設追加、プラン・オプション管理画面、利用状況、オンボーディング、データ移行
- PHASE 7：別途計画。法人横断、職員・シフト、会議音声AI、外部連携、老健等の業態追加、法人をまたぐ所属

合計の目安：PHASE 2a〜4 で約22週。2b-1 の完了時点から、架空データの検証環境で施設に画面を見ていただき、意見を反映する。

## 3. 効果測定の準備（PHASE 5 のため）

| 項目 | 方法 | 時期 |
|---|---|---|
| 導入前の基準値 | 施設長・事務長・事務員に、2〜4週間、対象業務（期限管理、提出物の回収・督促、書類探し、会議録・委員会記録）の作業時間を記録していただく（記録用紙を当社が用意） | ヒアリング時に依頼、PHASE 2 期間中に実施 |
| 導入後の利用 | 利用記録（日次の利用者数、画面別の利用、通知から対応までの時間、代理登録率、職員のログイン率） | PHASE 2a から記録 |
| 導入後の作業時間 | 基準値と同じ方法で再計測 | PHASE 5 |
| 期限超過・提出漏れ | 導入前は把握している範囲、導入後はシステムの集計 | PHASE 5 |

## 4. 作らないもの（現時点）

- 入居者（利用者）の介護情報・医療情報を扱う機能
- 介護ソフト・請求ソフトの置き換え
- 複雑な従量課金
- AI による自律的な登録・通知・承認
- ネイティブアプリ（スマホ対応 Web で対応）
- 外部連携（CSV で代替。アプリ外への通知手段は D-1）
- 一般職員による業務の作成（自分用メモ）
- 法人をまたぐユーザーの所属
