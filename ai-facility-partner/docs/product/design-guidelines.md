# デザインガイドライン（v1 案）

- 作成：2026-11-21（状態：**提案・承認待ち**）
- 根拠：他業界の製品リサーチ（`benchmark-research.md`）と、公開の基準（デジタル庁デザインシステム、GOV.UK Design System、SmartHR デザインシステム）
- 視覚の基礎（文字・色・ボタン・入力）は**デジタル庁デザインシステムに準拠**する。日本の行政サービスの基準で、高齢の方や IT が苦手な方を含む利用を前提にしており、公開・再利用を前提にしているため（利用条件は `benchmark-research.md` 第6章）
- 他社の画面・ブランド・文言はコピーしない。配色・名称・画面の構成は本製品独自のもの

---

## 1. デザイン原則

| 原則 | 意味 | 画面での例 |
|---|---|---|
| ① 今日やることから始める | ログインしたら、まず「今日やること」と「対応が必要なこと」だけが見える | 職員ホームは今日のやること中心。管理者ダッシュボードは「要対応」が最上段 |
| ② 職員の操作は1画面に1つのこと | 1つの画面で尋ねること・決めることは1つ。迷わず、スマホで片手で進める | 提出は「内容の確認 → 撮影 → 送信」の3画面。完了報告は1画面1ボタン |
| ③ 状態は少なく、言葉と色で示す | 状態の種類を増やさない。色だけに頼らず、文字とアイコンを必ず添える。赤は「期限超過」と「エラー」だけ | 「完了」は色を付けない静かな表示。注意が必要なものだけ色付きのラベル |
| ④ 通知は静かに | まとめて、必要な人にだけ届ける。通知の受け口は1つ | 同じ時間帯の通知を1通にまとめる。督促は未提出の人だけ |
| ⑤ その場で終わらせる | 画面を行き来させない | 通知・承認待ち一覧から、その場で承認・差し戻し。提出物はまとめて承認 |
| ⑥ 根拠を見せる | AI の回答、法令の根拠、提出の控えなど、「なぜそう言えるか」を同じ画面に示す | AI の回答の下に根拠のカード。業務詳細に根拠と控え |
| ⑦ 確認は取り返しのつかない操作だけ | 何でも「よろしいですか？」と聞かない。聞くときは件数と結果を書く | 「42名に催促を送ります。未提出の8名にだけ届きます」 |

## 2. 視覚の基礎

### 2.1 文字

| 項目 | 基準 |
|---|---|
| フォント | Noto Sans JP（数字・英字も同じ）。等幅が必要な場所は Noto Sans Mono |
| 最小サイズ | **16px**。16px 未満は使わない（デジタル庁の基準：16px 以上が基準値、14px は基本的に使わない） |
| 本文 | PC：16px、行の高さ 1.7。職員用スマホ：17px、行の高さ 1.7 |
| 見出し | 画面名 24px（スマホ 22px）、見出し 20px、小見出し 18px。いずれも太字、行の高さ 1.4〜1.5 |
| 件数（ダッシュボード） | 32px 太字。必ず単位（件・名）を添える |
| 禁止 | 日本語の斜体、文字の詰めすぎ（字間は0〜2%） |
| 拡大 | 画面を200%に拡大しても、横スクロールなしで読める（スマホ幅のレイアウトに切り替わる） |

### 2.2 色

すべての文字は背景に対して**4.5:1以上**（文字の大きさにかかわらず）、部品の境界・アイコンは**3:1以上**。下表の値は計算で確認済み。

| 用途 | 文字色 / 背景色 | コントラスト比 |
|---|---|---|
| 本文 | #1A1A1A / #FFFFFF | 17.4 |
| 補足文 | #4D4D4D / #FFFFFF | 8.45 |
| 主色（ボタン・リンク） | #0B5E8A / #FFFFFF（白文字のボタンも 7.04） | 7.04 |
| 主色（押したとき） | #084A6D / #FFFFFF | 9.50 |
| 期限超過・エラー | #B42318 / #FDECEA（白背景では 6.57） | 5.75 |
| 期限が近い・要修正 | #7A4100 / #FFF3D6 | 7.37 |
| 進行中・確認待ち | #1849A9 / #E8F0FE | 7.15 |
| まだ始められない・対象外 | #5C5C5C / #FFFFFF | 6.69 |
| 入力欄の枠 | #767676 / #FFFFFF（非テキスト3:1以上） | 4.54 |
| 画面の背景 | #F5F6F7（本文 16.08、補足 7.81、主色 6.51） | — |
| 区切り線（装飾） | #DADADA | （装飾のため対象外） |

- **色だけで意味を伝えない**：状態は必ず文字（「2日超過」など）とアイコンを添える
- **赤は期限超過・エラー・削除の操作だけ**に使う（他の状態に赤を使うと本当に危ないものが目立たなくなる）
- 本製品の主色は落ち着いた青緑系（#0B5E8A）。施設ごとの色の変更は PHASE 6 以降

### 2.3 フォーカス（キーボードで選ばれている場所）

- 黒（内側 2px）と黄色 #FFD43B（外側 4px）の二重の枠で示す（どの背景でも見えるように。黄色だけでは白い背景に対して1.43:1しかない）
- フォーカスの表示を消さない

### 2.4 余白・形・アイコン

| 項目 | 基準 |
|---|---|
| 余白 | 4・8・12・16・24・32・48px の段階だけを使う |
| 角の丸み | カード 8px、ボタン・入力 6px、ラベル（状態）丸型 |
| 影 | 使わない（境界は線で示す）。重なる部品（メニュー・ダイアログ）だけ薄い影 |
| アイコン | 線の太さ・大きさをそろえた1種類のアイコン集（Material Symbols を候補。利用条件は Apache License 2.0）。アイコンだけのボタンは作らず、文字を添える（下部タブも「ホーム」等の文字付き） |
| 画面の幅 | PC は最大 1,200px。スマホは左右 16px の余白で1列 |

### 2.5 表示の明るさ（ダークモード）

MVP はライト表示のみ。夜勤中の暗い場所での利用について職員の声を聞き、PHASE 5 以降にダークモードを検討する。

## 3. 部品

### 3.1 ボタン

| 種類 | 見た目 | 使う場面 | 数 |
|---|---|---|---|
| 主ボタン | 塗り（主色・白文字） | その画面で一番大事な操作（提出する、承認する） | **1画面に原則1つ** |
| 副ボタン | 枠線 | 主ボタン以外の選択肢（差し戻す、下書き保存） | 同じ場所に3つまで |
| テキストボタン | 文字だけ | 中止・キャンセル・戻る | 1画面に原則1つ |
| 危険ボタン | 赤 | 削除など取り返しのつかない操作（確認ダイアログの中だけ） | 一覧の各行に置かない |

| 項目 | 基準 |
|---|---|
| 高さ | 標準 48px。職員用スマホの主ボタンは 56px・横幅いっぱい。表の中の小さいボタンは 36px（押せる範囲は上下の余白で44px 以上を確保） |
| 押せる範囲 | 44px×44px 以上 |
| 配置 | PC：進む操作（完了、次へ）を右、戻る・キャンセルを左。スマホ：主ボタンは画面下に固定 |
| 文言 | 動詞で何が起きるかを書く（「提出する」「完了を報告する」「差し戻す」「催促を送る」）。「OK」「はい」は使わない |
| 押せない状態 | なるべく作らない。作る場合は、ボタンの近くに理由と押せるようになる条件を書く（例：「必要な書類が1件足りません」） |

### 3.2 入力

| 項目 | 基準 |
|---|---|
| 項目名 | 入力欄の上に置く。補足（入力の条件・例）は項目名の下に短く |
| 必須・任意 | 「※必須」「※任意」を文字で書く（記号だけにしない） |
| 入力欄の中の薄い文字 | 補足の代わりに使わない |
| 文字の種類 | 全角・半角などを制限しない（必要なら送信時に自動で変換） |
| エラー | 入力の途中では出さず、送信時に出す。項目のすぐ下に「何が起きたか・原因・どう直すか」を書き、画面の上にもまとめて表示 |
| 再入力 | 一度入力した情報を再び入力させない（前回の値を表示する） |
| 高さ | 48px（職員用スマホは 56px） |

### 3.3 状態のラベル

内部の状態（英字のコード）と、画面に出す言葉を分ける。**職員と管理者で同じ言葉を使う**（現場で会話するときにずれないように）。

業務：

| 内部 | 表示 | 見た目 |
|---|---|---|
| not_started | 未着手 | 色なしの文字 |
| in_progress | 進行中 | 青のラベル |
| awaiting_submission | 提出待ち | 青のラベル |
| awaiting_approval | 承認待ち | 青のラベル |
| returned | 差し戻し | 黄のラベル＋「!」アイコン |
| completed | 完了 | 色なしの文字＋チェックアイコン |
| on_hold | 保留 | 灰色のラベル |

提出物（対象者ごと）：

| 内部 | 表示 | 見た目 |
|---|---|---|
| not_submitted | 未提出 | 色なしの文字 |
| not_submitted（期限後） | 未提出（期限超過） | 赤のラベル＋「!」アイコン |
| submitted | 提出済み（確認待ち） | 青のラベル |
| approved | 承認済み | 色なしの文字＋チェックアイコン |
| returned | 差し戻し | 黄のラベル＋「!」アイコン |
| excluded | 対象外 | 灰色の文字 |

状態とは別の印（状態に重ねて表示）：

| 印 | 表示 | 見た目 |
|---|---|---|
| 期限超過 | 「2日超過」 | 赤のラベル |
| 期限が近い | 「あと2日」「今日まで」 | 黄の文字 |
| 例外完了・自己承認・代理登録・遅延 | 「例外完了」等 | 灰色の小さな注記 |
| アカウントなし | 「アカウントなし」 | 灰色の注記＋人のアイコン |
| AI の作成物 | 「AIの回答」「AI下書き」 | 灰色の枠のラベル（目立たせすぎない） |

作業一覧（はじめての設定・年度更新）：「完了」（色なし）／「未完了」（青のラベル）／「まだ始められない」（灰色の文字、押せない）

### 3.4 カード・一覧・表

| 部品 | 基準 |
|---|---|
| カード | 1枚に1つの業務・依頼。見出し・期限（相対表示）・誰から・主な操作1つ |
| 一覧 | 最初に見せるのは5件まで。それ以上は「すべて見る（n件）」 |
| 表 | 1行1人・1件。状態で並べ替え・絞り込み（「未提出」「差し戻し」などの絞り込みボタン）。値がない項目は空白、該当しない項目は「-」 |
| まとめ | 表の上に「42名中28名が提出」など、まず全体の数を書く |

### 3.5 通知

- 受け口は1つ（通知一覧 C03）。「要対応」（承認依頼・差し戻し・今日が期限）と「お知らせ」の2つに分ける
- 職員への通知は**まとめて送る**：同じ人・同じ送信時間帯の通知は1通にまとめる（例：「今日が期限の提出が2件あります」）。差し戻しと承認依頼はすぐに送る
- 管理職には週1回のまとめ（今週の期限・期限超過・承認待ち）をメールで送る（メールは PHASE 3）
- 通知の本文には個人情報を書かない（`architecture/security-design.md` 第3.4節）

### 3.6 確認ダイアログ

| 出す | 出さない |
|---|---|
| 削除、一括承認、多数への催促、取消、権限の変更、出力 | 1件の承認、完了報告、保存など、元に戻せる・影響が小さい操作 |

- 書くこと：対象の件数と、実行すると何が起きるか（例：「8名に催促を送ります。すでに提出した人には届きません」）
- ボタン：実行する操作の動詞（「催促を送る」）と「キャンセル」（テキストボタン）。離して配置する

### 3.7 データがない・読み込み中・つながらない

| 状態 | 表示 |
|---|---|
| まだ登録がない（未登録） | 何がここに表示されるかと、次にやること（権限がある人には登録のボタン） |
| 条件に合うものが0件 | 「0件」と、条件の解除の案内（「未登録」と区別する） |
| 読み込み中 | 画面の骨組みを先に出す（白い画面で待たせない） |
| 通信できない | 「通信できませんでした。入力内容はこの端末に保存しています。つながったら自動で送ります」 |
| 時間切れでログアウト | 入力中の内容を保持し、ログイン後に戻す。自動ログアウトの1分前に「続けますか」を出す |

## 4. 画面のパターン

| パターン | 使う場所 | 要点 |
|---|---|---|
| P1 今日のやること | 職員ホーム（S01） | 上から「差し戻し → 期限超過 → 今日まで → 依頼（未読） → 今週の予定」。各カードに主な操作1つ。毎日の業務は「今日のチェックリスト」にまとめ、1タップで完了 |
| P2 1画面1つの手続き | 提出（S03）、完了報告、初回登録（C05） | 1画面1つの質問・操作。上に「戻る」、下に主ボタン。進み具合の表示はまず付けない。途中の内容は自動で保存 |
| P3 作業一覧 | はじめての設定（A31）、年度更新（A06） | 作業ごとに状態（完了／未完了／まだ始められない）。順番が決まっている作業は「まだ始められない」で示す |
| P4 提出状況表 | A09 | 全体の数 → 絞り込み → 1人1行 → まとめて承認・催促・印刷 |
| P5 その場で承認 | 通知一覧（C03）、承認待ち（A10） | 内容と証拠を横（スマホは下から出る画面）に表示し、承認・差し戻しをその場で。差し戻しは理由必須 |
| P6 見通し | 職員：週の帯（予定のある日に印）／管理者：月×カテゴリの一覧 | 「今日」から先の予定を一目で |
| P7 根拠付きの回答 | AI アシスタント（A20） | 「AIの回答」のラベル → 回答 → 根拠のカード（業務・書類・提出状況へのリンク）→ 対象期間・データの更新時刻 → 「回答が正しくない」の報告。外部の画像・リンクは表示しない |
| P8 印刷 | 未提出者一覧、年間行事表、委員会の記録 | A4 縦、白黒でも状態が分かる（文字で表示） |

## 5. 文章のルール

### 5.1 書き方

- です・ます調。一文は50文字程度まで。並べる情報は箇条書き
- 常用漢字を基本にする。専門用語・略語には短い説明を添える（例：「BCP（災害時などの業務継続計画）」）
- 主語と助詞を省かない。二重否定を使わない（「できないことはありません」→「できます」）
- 「！」などの強調、責める言い方を使わない（「提出されていません！」→「まだ提出されていません」）
- 3桁以上の数字にはカンマ（1,200件）

### 5.2 用語（画面で使う言葉を1つに決める）

| 使う言葉 | 意味 | 使わない言葉 |
|---|---|---|
| 業務 | 期限のある仕事（年間業務・臨時業務） | タスク、ジョブ |
| 依頼 | 管理者から職員への業務の依頼 | 指示、アサイン |
| 提出 | 職員が書類や情報を出すこと | アップロード（操作の説明以外） |
| 確認・承認 | 提出物・業務の内容を見て認めること（確認者・承認者） | レビュー |
| 差し戻し | 直してもう一度出してもらうこと | 却下、リジェクト |
| 期限 | 守るべき日（時刻） | 締め切り、デッドライン（混在させない） |
| 今日のやること | 職員ホームの見出し | ToDo |
| 書類 | 保管するファイル | ドキュメント |

施設で別の呼び方をしている場合は、ヒアリングで確認して用語を変更する（【要確認】）。

### 5.3 日付・期限・数

| 項目 | 書き方 |
|---|---|
| 日付 | 「11月20日(木)」。年が違うときだけ「2027年4月1日(木)」 |
| 期限 | 日付に相対表示を添える：「今日まで」「あと2日」「2日超過」 |
| 時刻 | 「17:00まで」 |
| 人数・件数 | 「42名中28名が提出」「3件」 |

### 5.4 エラー・案内の文の型

「何が起きたか → 原因 → どう直すか」の順。場所が足りなければ「原因 → どう直すか」を優先。

| 悪い例 | 良い例 |
|---|---|
| エラーが発生しました | ファイルを送れませんでした。ファイルの大きさが 25MB を超えています。写真を撮り直すか、小さいファイルを選んでください |
| 入力に誤りがあります | ＊期限を入力してください。今日より後の日付を選べます |
| 権限がありません | この業務を承認できるのは、指定された承認者（佐藤さん）です |

### 5.5 ボタン・見出しの言葉

- ボタンは動詞：「提出する」「完了を報告する」「承認する」「差し戻す」「依頼を送る」「催促を送る」「印刷する」
- 画面の見出しはその画面でやること：「研修レポートを提出する」「提出状況（感染症研修レポート）」

## 6. アクセシビリティ

| 項目 | 目標・基準 |
|---|---|
| 目標 | JIS X 8341-3:2016 適合レベル AA（WCAG 2.2 AA も参照） |
| 色 | 第2.2節。色だけで区別しない |
| 拡大 | 200%拡大で利用可能 |
| キーボード | すべての操作がキーボードでできる。フォーカスが見える |
| 読み上げ | 入力欄・ボタン・アイコンに読み上げ用の名前を付ける |
| 時間制限 | 自動ログアウト以外に時間制限を設けない。自動ログアウトの前に延長できる |
| 動き | 点滅・自動で動く表示を使わない |

## 7. 確かめ方

- 受入テスト（`development/test-strategy.md` 第7章）で、IT が苦手な職員・夜勤者を含む人に、主要な操作を説明なしで試してもらう
- 判定：説明なしで「提出」「完了報告」ができるか、迷った場所はどこか、文字は読めるか
- テスト11（スマホ）の判定項目に、本書の基準（文字16px以上、ボタン、3タップ以内）を使う
- 自動の検査：コントラスト、読み上げ用の名前、キーボード操作をCIで確認（アクセシビリティ検査ツール）
