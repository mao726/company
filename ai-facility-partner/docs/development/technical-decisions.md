# 技術的な判断の記録

重要な設計判断は、理由と影響範囲をここに記録する。状態は「提案」「承認」「却下」「置き換え」「要決定」のいずれか。
**「提案」「要決定」は未決定であり、事業責任者の承認前に実装の前提にしない。**

## 設計レビュー記録（2026-11-17）

PHASE 1 の初稿作成後に見直しを行い、以下を修正した。

| 見つかった問題 | 放置した場合の影響 | 修正 |
|---|---|---|
| 職員の部署・役職を職員台帳に直接持っていた | 異動で過去の所属が上書きされ、「当時の担当者・承認者の役職」が分からなくなる | TD-013 |
| 法人ID・施設IDが列にあるだけで、参照先の法人一致を保証していなかった | アプリの不具合で他法人の職員を担当者に設定できてしまう | TD-014 |
| RLS の設定方法が未定義 | 共有接続で前の利用者の設定が残る、設定漏れで全件が見える | TD-015 |
| 認証サービスを前提にしていた | メールのない職員がログインできず、利用が広がらない | TD-016 |
| 通知を事前予約する設計だった | 期限変更後に古い期限で通知、提出済みの人に督促 | TD-017 |
| 常駐ワーカー前提だった | 実証期の構成では動かない | TD-018 |
| 指示書の PHASE 2 と 3 の依存関係 | PHASE 2 で提出物回収が完成しない、操作履歴の欠落 | TD-020 |
| 祝日による期限の前倒しで期間がずれる可能性 | 同じ月の業務が二重に生成される | 期間キーは移動前の本来の期間で決定（database-design 第5章） |
| 当社提供の法令要件候補の改定時の扱いが未定義 | 施設が確認した記録を当社が上書きしてしまう | TD-023 |
| ログインしない職員への通知・回収 | 提出状況表が埋まらず実運用できない | TD-026（代理登録・アカウントなし表示） |
| 自由記述の文章の仮名化の限界 | 入居者名などが AI 事業者に送られる | security-design 第4章（機能ごとに有効化を判断） |
| ダッシュボードの「AIからの確認事項」 | PHASE 4 前に AI 機能があるように見える | TD-027 |
