# テスト戦略

## 1. 方針

- 重要な業務処理（権限、分離、期限、繰り返し、通知、承認）は**自動テスト必須**。テストが通らない変更は取り込まない
- テストデータは**架空データのみ**。実在の施設・職員・入居者の情報は使わない
- 「今日」に依存する処理は、時刻を外から差し替えられる設計にし、テストで任意の日時を再現する
- 画面だけ・ダミー表示だけの機能は完成扱いにしない（完成＝自動テスト合格＋実データ相当の検証環境で動作確認）

## 2. テストの種類

| 種類 | 対象 | 道具 | 実行 |
|---|---|---|---|
| 静的検査 | 型、コード規約、モジュール依存ルール、秘密情報の混入 | TypeScript、ESLint、秘密情報スキャン | 変更ごと（CI） |
| 単体テスト | 権限判定、状態遷移、期限・期間キーの計算、祝日、設定の階層解決、契約判定 | Vitest | 変更ごと |
| 結合テスト（実DB） | RLS、API、マイグレーション、繰り返し生成、通知の算出 | Vitest＋Docker の PostgreSQL | 変更ごと |
| E2E（画面） | 主要業務の通し操作（PC・スマホ） | Playwright（スマホ表示を含む） | 変更ごと（主要経路）、毎日（全体） |
| 負荷・規模 | 施設数・職員数が多い場合の整合性と速度 | 生成データ＋計測スクリプト | フェーズ完了時 |
| 復元訓練 | バックアップからの復旧 | 検証環境 | PHASE 3 以降、四半期ごと |
| AI 評価 | 根拠付き回答、推測しないこと、権限外の非表示 | 評価セット＋自動採点 | AI 関連の変更ごと |
| セキュリティ | 依存部品の脆弱性、主要な攻撃（ID書換え、権限昇格、XSS、CSRF） | スキャナ＋専用テスト、外部診断 | 週次／リリース前 |

## 3. 必須テスト12項目の実施方法

| No | 必須テスト | 実施方法・合格基準 |
|---|---|---|
| 1 | 法人Aの職員が法人Bのデータを見られない | 2法人を生成。法人Aの全役割で、法人Bの**全種類のデータ**（全API・全テーブル）に対し取得・一覧・更新・削除・ダウンロードを試行し、すべて 404/0件。DB層でも RLS 下で法人BのIDを指定した SQL が0件。新しいテーブル・APIを追加した際に**テスト対象から漏れないよう、テーブル一覧と API 一覧から自動で対象を作る** |
| 2 | 施設Aの一般職員が施設Bの情報を閲覧できない | 同一法人の2施設で同様。法人管理者は**許可された施設のみ**閲覧できることも確認 |
| 3 | 承認権限のない職員は承認できない | 役割×権限×適用範囲の全組合せの表から生成したテスト。STAFF が承認APIを呼ぶと 403、承認履歴に記録されない |
| 4 | 期限超過の業務が正しく表示される | 時刻を固定し、期限前日・当日・翌日、完了・保留・取消、施設のタイムゾーン境界（日本時間0時前後）でダッシュボードと一覧の件数を検証 |
| 5 | 繰り返し業務が二重生成されない | 同じ生成処理を連続実行・**同時並行実行**しても1期間1件。シリーズ変更後、年度更新後、祝日移動時も検証 |
| 6 | 提出期限の通知が正しいタイミングで送られる | 時刻を進めながら通知処理を実行し、期限3日前・1日前・当日・超過翌日に**未提出者だけ**に1回ずつ送られること、提出済み・対象外には送られないこと、期限変更後は新しい期限で送られること、設定変更が反映されること |
| 7 | 承認・差し戻しの履歴が残る | 承認→差し戻し→再提出→承認の後、全履歴（実行者・日時・理由・対象版）が残り、更新・削除できない（DB権限でも拒否） |
| 8 | ファイルのアクセス制限が機能する | 他施設・権限外・アクセスレベル外のダウンロードが拒否される。期限切れのダウンロードURLは使えない。保管領域に直接アクセスできない。ウイルス検査前は取得不可 |
| 9 | AIが存在しない情報を回答した場合に検知・確認できる | 評価セットの「存在しない委員会・職員・期限」を問う質問で、作り話が出ないこと、または根拠照合で「根拠と一致しない」と検出・表示されること。利用者の誤り報告が記録されること |
| 10 | バックアップから復旧できる | 検証環境で時点復元を実行し、件数・ハッシュ値・参照整合性のチェックを自動実行。所要時間を記録（目標：24時間以内） |
| 11 | スマートフォンで主要操作ができる | 代表的な画面幅（iPhone SE 相当、一般的な Android）で、ログイン→依頼の確認→完了報告→提出（撮影代替のファイル選択）→通知確認を自動操作。ボタンサイズ・横スクロールなしを確認 |
| 12 | 施設数・職員数が増えても整合性が保たれる | 生成データ（例：100法人・1,000施設・10万職員・数百万件の業務）で、分離テストの再実行、繰り返し生成の完了時間、ダッシュボードの応答時間（目標：2秒以内）、参照整合性チェック |

## 4. テストデータ

- 架空データ生成器を用意（法人・施設・職員・年間業務・提出依頼・書類のダミーファイル）
- 開発・検証環境の初期データはこの生成器のみで作成。本番環境では初期データ投入を**設定で禁止**
- 生成データには「架空」と分かる名称を使う

## 5. CI での合否基準

| 段階 | 失敗時 |
|---|---|
| 型・規約・依存ルール・秘密情報スキャン | 取り込み不可 |
| 単体・結合・分離テスト | 取り込み不可 |
| E2E（主要経路） | 取り込み不可 |
| 脆弱性スキャン（重大） | 取り込み不可（例外は理由を記録） |
| カバレッジ | 権限・状態遷移・期限計算のモジュールは分岐をすべて網羅 |

## 6. 受入テスト（施設による確認）

- PHASE 2b・3・4 の完了時に、架空データの検証環境で施設長・事務長に業務シナリオを操作していただく
- 確認シナリオ例：年間業務の登録、業務依頼から完了承認、提出物回収と督促、委員会の決定事項から改善完了、AI への質問
- 指摘は一覧化し、対応・見送りを記録
