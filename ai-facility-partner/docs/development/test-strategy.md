# テスト戦略

- 版：v2（2026-11-17 設計レビューの指摘を反映：合格基準を測定可能にし、テストとフェーズの対応を1つの表に統一）

## 1. 方針

- 重要な業務処理（分離、権限、期限、繰り返し、通知、承認、ファイル）は**自動テスト必須**。テストが通らない変更は取り込まない
- テストデータは**架空データのみ**。実在の施設・職員・入居者の情報は使わない
- 「今日」「現在時刻」に依存する処理は、時刻を外から差し替えられる設計にし、テストで任意の日時を再現する
- 完成の定義：自動テスト合格＋検証環境（架空データ）で動作確認＋該当する受入確認。画面だけ・ダミー表示だけの機能は完成扱いにしない

## 2. テストの種類

| 種類 | 対象 | 道具 | 実行 |
|---|---|---|---|
| 静的検査 | 型、コード規約、モジュール依存ルール、`withTenantTx` を通らない DB アクセス、秘密情報の混入 | TypeScript、ESLint、秘密情報スキャン | 変更ごと（CI） |
| DB 構成の検査 | 全テナントテーブルで RLS が有効・強制か、追記のみのテーブルに UPDATE/DELETE 権限がないか、アプリ用DB利用者が RLS を迂回できないか | SQL によるカタログ検査 | 変更ごと |
| 単体テスト | 権限判定、承認者の判定式、状態遷移、期限・発生日の計算、祝日、設定の階層解決、契約判定、送信フィルタ | Vitest | 変更ごと |
| 結合テスト（実DB） | RLS、API、マイグレーション、繰り返し生成、通知の算出・送信、ジョブの並行実行 | Vitest＋Docker の PostgreSQL | 変更ごと |
| E2E（画面） | 主要業務の通し操作（PC・スマホ・タブレット） | Playwright | 変更ごと（主要経路）、毎日（全体） |
| 規模・性能 | 第3章 テスト12 | 生成データ＋計測スクリプト | フェーズ完了時 |
| 復元訓練 | 第3章 テスト10 | 本番と同じ統制の一時的な復元先 | PHASE 3 以降、四半期ごと |
| AI 評価 | `architecture/ai-architecture.md` 第6章 | 評価セット＋自動採点 | AI 関連の変更ごと |
| ログの個人情報 | アプリのログ・エラー監視に氏名・本文・ファイル名が出ないこと | ログを取得して検査 | 変更ごと |
| セキュリティ | 依存部品の脆弱性、主要な攻撃（ID 書換え、権限昇格、XSS、CSRF、ファイル） | スキャナ＋専用テスト、外部診断 | 週次／リリース前 |

## 3. 必須テスト12項目の実施方法と合格基準

### テスト1・2：法人間・施設間の分離

- 対象の作り方：DB のテーブル一覧と API の一覧から**自動で対象を作る**（新しいテーブル・API が対象から漏れない）
- 期待結果：テーブルの種類（`database-design.md` 第2.2節）ごとに定義

| 種類 | 他法人（テスト1）・他施設（テスト2）の利用者からの期待結果 |
|---|---|
| S：システム専用 | 読める（共通マスタ）。書けない（アプリ用DB利用者に書込み権限なし） |
| W：処理用 | アプリ用DB利用者からは読み書きできない（ジョブの登録は専用関数のみ。他施設の施設IDを指定すると拒否） |
| T-M：施設・法人の混在 | 他施設の行は0件。法人共通の行は読めるが、法人単位の権限がなければ書けない |
| C：混在マスタ | システム標準の行だけ読める。他法人・他施設の行は0件。システム標準の行は書けない |
| T-F：施設データ | API：404。DB（RLS 下の SQL）：0件、更新・削除0行 |
| T-O：法人データ | 他法人：0件。同じ法人の利用者：読めるが、法人単位の権限がなければ書けない。facilities は、文脈の施設と自分に役割割当がある施設だけ見える |
| T-P：職員・ユーザー・役割割当・ログイン履歴 | 他法人：0件。同じ法人の他施設：その施設に所属履歴のない職員は0件 |

追加のケース：
- 施設A・Bの両方に役割割当がある利用者：施設Aの文脈では施設Bのデータが0件（文脈の施設だけ）
- 法人管理者：許可された施設だけ読める。許可されていない施設は404・0件
- 支援アクセス（app_support）：許可がない・期限切れ・取消済み・許可と異なる法人や施設を文脈に設定した場合は、**すべての種類のテーブル**で0件。有効な許可では許可された施設の行だけ読め、法人共通の行は読めず、書けない。操作履歴は専用関数で記録される
- 専用関数：各関数が範囲外の対象（他施設の職員、他法人の施設など）を拒否する
- 保護された役割（CORPORATE_ADMIN・FACILITY_DIRECTOR）を Web アプリの DB 利用者で割り当てると DB が拒否する
- 定期処理：施設ごとの文脈で、他施設のデータを読まない・書かない
- ファイル：他施設のファイルのダウンロードURL発行・取得が拒否される
- 文脈が未設定の SQL：テナントデータは0件
- DB の直接公開 API（ホスティングの機能）が無効であること

### テスト3：承認権限

権限表（`permission-design.md` 第8章）と承認者の判定式（第6章）から**自動生成**したテスト。

| ケース | 期待結果 |
|---|---|
| 一般職員が承認 API を呼ぶ | 403、承認履歴に記録されない |
| 承認権限を持つが、指定された承認者ではない人 | 403 |
| 指定された承認者だが、対象を含む範囲の権限がない人 | 403（作成時に別の承認者に回されることも確認） |
| 他部署の部署管理者 | 403 |
| 自己承認 | 予備の承認者に回る。予備の承認者本人の業務で他に承認者がいない場合のみ自己承認として記録 |
| 対象の種類 | 業務・提出物・議事録のすべてで上記を確認。研修の受講確認・要件の確認済み設定も権限のない人は 403 |
| 施設をまたぐ権限 | 施設Aで部署管理者・施設Bで一般職員の人が、施設Bで承認できない |
| 権限昇格の防止 | 自分への役割割当、自分の権限を超える役割の割当、施設長による法人管理者の割当、最後の施設長の解除が、すべて拒否される |

### テスト5：繰り返し業務の生成（二重生成なし・欠落なし）

| ケース | 期待結果 |
|---|---|
| 同じ生成処理の連続実行・**同時並行実行** | 発生日ごとに1件 |
| 毎週月・木 | 両方の曜日の業務が作られる（欠落なし） |
| 祝日による前倒し・後ろ倒し | 期限日だけ移動し、発生日は変わらない。二重にならない |
| 人が取り消した回 | 翌日以降の生成で復活しない |
| ルール変更（境界日指定） | 境界日前は旧ルール、境界日以降は新ルールの回だけが存在し、旧ルールの境界日以降の未着手の回は取消になっている |
| 年度の境界・年度更新後 | 二重にならず、旧年度の記録は変わらない |
| 年度開始月・週の開始曜日の設定変更 | 既存の業務が増減しない |
| 担当者が退職済み | 担当者未設定で作られ、警告が出る |
| 欠落の検知 | 意図的に1件削除したデータで、生成処理が不足を作成・警告する |
| 完了日ベース（PHASE 3） | 完了→再開→再完了で次回分は1件 |

### テスト6：通知のタイミング

`database-design.md` 第4.10節の既定の通知表から期待結果を作り、時刻を進めながら通知処理を実行する。

| ケース | 期待結果 |
|---|---|
| 提出期限の3日前・1日前・当日・超過翌日 | 未提出・差し戻し中の対象者に、**チャネルごとに1回ずつ**。提出済み・承認済み・対象外には送られない |
| 超過翌日の依頼者 | 依頼ごとに1通（「未提出 n名」） |
| 期限の変更 | 古い期限の未送信分は取消、新しい期限で送られる |
| 設定の変更（施設・法人のロック） | 変更後の設定で送られる。法人がロックした項目は施設で変更できない（法人の設定画面は PHASE 7 のため、2b-1 ではテスト用に法人の設定を直接登録して確認） |
| 受信時間帯（施設・本人） | 時間外は送らず、次の送信可能時刻に送る |
| 定期処理の停止と再開 | 本来の送信時刻から24時間以内のものだけ送り、それ以外は「送信せず」として記録 |
| 並行実行 | 二重に送られない |
| 送信失敗 | 3回まで再送し、失敗は管理者画面に表示 |
| 業務の期限・依頼・承認依頼・差し戻し | 既定の通知表どおり |

### テスト7：承認・差し戻しの履歴

| ケース | 期待結果 |
|---|---|
| 承認 → 差し戻し → 再提出 → 承認 | 全履歴（実行者・日時・理由・対象の内容のハッシュ値）が残る |
| 承認者の付け替え・取消 | 理由付きで記録される |
| 承認後の内容変更 | 「承認後に変更あり」と表示され、再承認の依頼ができる。優先度だけの変更では表示されない |
| DB での更新・削除 | 追記のみのテーブル（承認・状態履歴・提出・書類の版・議事録・操作履歴）への UPDATE・DELETE が DB の権限で拒否される |
| 対象の種類 | 業務・提出物・議事録のすべて（受講確認・要件の確認は承認ではない単独の確認行為なので対象外。権限はテスト3、履歴は操作履歴で確認） |

### テスト8：ファイルのアクセス制限

| ケース | 期待結果 |
|---|---|
| 他施設・他法人のファイル | 拒否 |
| アクセスレベル「管理職」の書類を一般職員が開く | 拒否 |
| 「限定」書類を閲覧者リストにない施設長が開く | 拒否 |
| 他の職員の提出物ファイル | 拒否（本人・確認者・確認権限の範囲内の人のみ可） |
| 提出物が書類の一覧・検索に出ない | 出ない |
| 期限切れのダウンロードURL | 使えない |
| 保管領域・隔離領域への直接アクセス | できない |
| ウイルス検査前のファイル | 取得できない |
| 許可されない形式・マクロ付き・拡張子と中身の不一致・サイズ超過 | 受け付けない |
| 位置情報付きの画像 | 保管されたファイルに位置情報がない。受領時と保存時のハッシュ値が記録されている |
| ダウンロード | 操作履歴に記録される |

### テスト9：AI が存在しない情報を回答した場合の検知

`architecture/ai-architecture.md` 第6章の評価セットと合格基準（作り話0件〔警告付きの表示も不合格〕、権限外0件、注入への追従0件、実名の送信0件、根拠付き回答率95%以上、0件時の定型表示100%、各質問3回実行）。

### テスト10：バックアップからの復旧

| 確認項目 | 合格基準 |
|---|---|
| 復旧時間（RTO） | 復元開始から利用可能まで24時間以内（実測値を記録） |
| 失ったデータ量（RPO） | 指定した時点と復元結果の差（最後の記録の時刻）を実測し、24時間以内 |
| DB の件数・参照整合性 | 主要テーブルの件数が一致、外部キー・一意制約の検査が全件合格 |
| ファイル | 別アカウントの複製から復元したファイルについて、`files.sha256_stored` と実体のハッシュ値が全件一致 |
| 権限 | 復元先で RLS が有効、アプリ用DB利用者の権限が本番と同じ |
| 切替手順 | 運用ガイドの手順どおりに切替（または必要なデータのみ戻す）ができる |
| 後片付け | 一時的な復元先が破棄されている |

## 5. テストデータ

- 架空データ生成器を用意（法人・施設・職員・所属・年間業務・提出依頼・書類のダミーファイル・規模試験用の大量データ）
- 開発・検証環境の初期データはこの生成器のみで作成。本番環境では投入処理を**無効化**
- 生成データには「架空」と分かる名称を使う

## 6. CI での合否基準

| 段階 | 失敗時 |
|---|---|
| 型・規約・依存ルール・秘密情報スキャン・DB 構成の検査 | 取り込み不可 |
| 単体・結合・分離テスト | 取り込み不可 |
| E2E（主要経路） | 取り込み不可 |
| ログの個人情報検査 | 取り込み不可 |
| 脆弱性スキャン（重大） | 取り込み不可（例外は理由を記録） |
| 網羅 | 権限判定・承認者の判定式・状態遷移・期限計算・送信フィルタは分岐をすべて網羅 |

## 7. 受入テスト（施設による確認）

- PHASE 2b-1・2b-2・3・4 の完了時に、架空データの検証環境で施設長・事務長・介護主任・一般職員（夜勤者を含む）に業務シナリオを操作していただく
- 確認シナリオ例：年間業務の登録、業務依頼から完了承認、提出物回収と督促・代理登録、委員会の決定事項から効果確認、AI への質問
- 指摘は一覧化し、対応・見送りを記録
- 判定項目に `product/design-guidelines.md` 第7章の観点を含める（説明なしで「提出」「完了報告」ができるか、迷った場所、文字が読めるか）。IT が苦手な職員・夜勤者を必ず含める
