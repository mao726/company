## 3. アカウントの管理

### 3.1 施設の職員

| 場面 | 手順 |
|---|---|
| 入職 | 職員台帳に登録 → 必要な場合のみ招待（ログイン可能に）→ 役割割当 → 「新規採用者を含む」研修の対象への追加（提案を確認） |
| 異動 | 所属（施設・部署・役職・職種）の期間を更新。役割の見直し |
| 退職 | 退職日を登録 → 退職日の翌日0時からログイン不可 → 引継ぎ対象の一覧を確認して担当を変更 |
| 即時停止 | 懲戒・端末紛失・不審なログイン時に、管理者が「即時停止」→ 全セッション失効 |
| パスワード・パスキーの再設定 | 本人が再設定。メールのない職員は管理者が再設定コードを発行（記録付き） |
| 施設長の交代 | 法人（契約者）からの書面の依頼に基づき、当社が本人確認のうえ新しい施設長を割り当てる |
| 権限の棚卸し（四半期） | 棚卸し画面で、役割の割当・最終ログイン日・長期未使用を確認し、実施を記録。**90日使われていない管理権限を持つアカウントは自動停止**、その他は警告 |

### 3.2 当社のインフラアカウント

| 項目 | 手順 |
|---|---|
| 対象 | ホスティング（アプリ・DB・ストレージ）、GitHub、AI 事業者、エラー監視、メール配信、DNS・ドメイン、バックアップ保管先 |
| 多要素認証 | 全員必須（パスキー・セキュリティキーを推奨） |
| 人数 | 本番に触れられる人は運用担当（2名以内）のみ。一覧を管理 |
| 管理キー | RLS を迂回する管理キーはアプリに設定しない。保管は秘密情報管理のみ |
| 棚卸し | 四半期ごとにアカウント・権限・キーを確認し記録 |
| 退職・異動 | 当日に権限を削除し、共有していた鍵・キーを入れ替える |

## 4. 当社による施設データへのアクセス

### 4.1 通常（障害対応・問い合わせ対応）

1. 施設からの問い合わせ、または障害の検知
2. 当社担当者が管理画面から理由を添えてアクセスを申請
3. 施設の `support_access.approve` 権限者（施設長・事務長）が承認（期限付き、既定24時間。ファイルの中身の閲覧を含めるかを選択）
4. アクセスは**読み取り専用**（DB で書込み拒否）。全操作を記録
5. 期限到来で自動失効。対応内容を施設に報告

### 4.2 緊急時（施設の承認を待てない場合：漏えい調査・重大障害）

1. 運営責任者と運用担当の**2名が承認**（理由・範囲・時間を記録）
2. 最短時間・最小範囲でアクセス（原則読み取り専用）
3. 全操作を記録
4. **事後、24時間以内に施設へ報告**
5. 契約書に緊急時アクセスの条件を明記する（`security-design.md` 第10章）

DB の直接操作（データ修正など）も同じ2名承認・記録・事後報告とする。

## 5. バックアップ・復旧

| 項目 | 内容（実証期の目標、仮） |
|---|---|
| バックアップ | DB：日次＋時点復元（7〜14日、プランに応じて）、別アカウントの書換え不可の保管領域へ日次の暗号化バックアップ（90日）。ファイル：別アカウントの版管理付き保管領域へ日次複製 |
| 復旧時間の目標（RTO） | 24時間以内 |
| 失ってよいデータ量の目標（RPO） | 24時間以内（時点復元が有効なら実際は数分） |

復旧手順：
1. 障害範囲の特定（DB、ファイル、アプリ、外部サービス）
2. アプリの不具合なら直前の版へ戻す
3. データの破損なら、破損前の時点を特定して**別の復元先に**時点復元（同じアカウントが使えない場合は別アカウントのバックアップから）
4. 復元先で件数・参照整合性・ファイルのハッシュ値・RLS とDB利用者の権限を確認
5. 切替え、または必要なデータのみ戻す
6. 施設へ報告、原因と再発防止策を記録

復元訓練（四半期）：
- 本番と同じ統制の**一時的な復元先**（本番アカウント内、アクセスは運用担当のみ）に復元し、`development/test-strategy.md` テスト10の項目を確認して記録
- **確認後に復元先を破棄**する（本番データを検証環境・開発環境に入れない）

AI 事業者・メール送信が停止した場合：業務は手作業で継続可能（AI 機能は停止表示、通知は再送）。

## 6. 障害・セキュリティ事故の対応

| 区分 | 例 | 対応 |
|---|---|---|
| 重大 | 他施設のデータが見えた、情報漏えいの疑い、不正アクセス、全面停止 | 直ちに該当機能を停止 → 運営責任者へ連絡 → 証拠保全（ログの退避） → 影響範囲の調査 → **施設へ24時間以内に第一報** |
| 中 | 一部機能の停止、通知の未送信 | 当日中に対応、施設へ連絡 |
| 軽 | 表示の不具合 | 通常の改修 |

個人データの漏えい等の疑いがある場合（法令上の骨格は `security-design.md` 第6章。詳細は要専門家確認）：
1. 第一報：疑いを認知してから24時間以内に施設へ（発生の可能性、影響範囲の見込み、当面の措置）
2. 中間報告：72時間以内（対象データ、人数、原因、二次被害のおそれ、再発防止策のうち判明分）
3. 施設が個人情報保護委員会への報告・本人への通知を期限内に行えるよう、調査結果を提供
4. 送信記録（AI に送ったレコード）・操作履歴・アクセスログから影響範囲を特定
5. 年1回の机上訓練で手順を確認

## 7. データの出力・削除

| 場面 | 手順 |
|---|---|
| 施設からの出力依頼 | 権限者が画面から出力（CSV＋ファイル一式、再認証あり）。出力は記録 |
| 解約 | 出力データを提供 → 契約で定めた期間経過後に削除 → 削除完了を報告（範囲は再委託先一覧に沿う。バックアップは保持期間の経過で消去されることを説明） |
| 保存期限の到来 | 通知 → 施設が確認して削除（自動削除はしない） |
| 要配慮個人情報等の混入 | 管理者が「隔離」→ 内容確認 → 削除（記録を残す） |
