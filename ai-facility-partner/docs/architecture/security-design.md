## 2. 取り扱うデータの区分と混入防止

| 区分 | 例 | MVP での扱い | AI への送信 |
|---|---|---|---|
| C1 業務情報 | 業務名、カテゴリ、期限、委員会名、業務説明 | 保存 | 用途ごとに許可したもののみ |
| C2 職員の基本情報 | 職員氏名、部署、役職、職種、ログインID | 保存（最小限） | **仮名に置き換えて送信**【仮定 Q4】 |
| C3 職員の機密情報 | 資格証の画像、連絡先、評価 | **扱いは要決定（D-8）**。扱う場合は「限定」アクセス・保存期限必須 | 不可 |
| C4 要配慮個人情報 | 入居者の心身の状況・病歴、職員の健康診断結果 | **ファイル・本文として保存しない** | 不可 |
| 対象外 | マイナンバー、年末調整書類 | 扱わない（利用規約と画面で明示） | 不可 |

混入を防ぐ仕組み（運用ルールだけに頼らない）：

| 場面 | 仕組み |
|---|---|
| 提出依頼の作成 | **データ区分の選択を必須**にする。C4 を選ぶと「ファイルを受け取らず、提出済み・確認済みだけを記録する」方式に強制（例：健康診断は「受診済み・結果提出済み」の記録のみ）。マイナンバーを含む書類は依頼できない旨を表示 |
| 書類の登録 | データ区分を必須にする（カテゴリの既定値を初期表示）。区分の値は `c1`・`c2`・`c3`・`c4_possible`（C4 を含む可能性あり）。`c4`（要配慮個人情報と分かっているもの）は書類として登録できない。委員会の議事録（`meeting_minutes` も既定 `c4_possible`）・事故関係のカテゴリは `c4_possible` を既定とし、AI 送信の対象外・アクセスレベル「管理職」以上を既定にする |
| アップロード時 | 「入居者の氏名・病状、マイナンバーを含む書類はアップロードしないでください」の確認表示 |
| AI 送信 | 保存された書類・議事録・提出物のうち `c3`・`c4_possible`・`c4` のものは AI に送らない（システムで拒否）。議事録下書きは、その場で入力するメモだけを送る（`ai-architecture.md` 第3章） |
| 混入が判明した場合 | 管理者が該当書類を「隔離」（`quarantined`、閲覧停止）→ 施設長の承認で、専用関数による完全削除（追記のみテーブルの版・抽出テキスト・議事録本文を含む）→ `purge_records` に記録（`database-design.md` 第4.12節）。バックアップからは保持期間の経過で消える |

C4 を本格的に扱う（例：委員会記録に入居者情報を含めて保存する）かどうかは、施設の運用・専門家の確認を経て別途判断する。

## 3. 対策一覧

### 3.1 アプリケーション

| 分類 | 対策 |
|---|---|
| 通信の暗号化 | HTTPS のみ（TLS 1.2 以上）、HSTS。DB・ストレージとの通信も TLS |
| 保存データの暗号化 | DB・ストレージ・バックアップを暗号化 |
| データの所在 | DB・ファイル・バックアップは国内リージョン【仮定 Q2】。ただし**事業者の所在国は別問題**（第5章） |
| 認証 | 認証サービスに委ねる（パスワードを自前で保管しない）。方式は D-2（職員のログイン方式）・TD-016 で確定 |
| 多要素認証 | **施設長・事務長・法人本部管理者・当社管理者、および保護された権限を持つ人は必須**。一般職員は施設設定で選択し、令和9年度までに全員必須とする計画（2省ガイドラインは多要素認証の早期採用を求め、安全管理ガイドラインは令和9年度時点で2要素認証を求める。第7.0版での扱いは要確認）。スマホを持たない職員の手段は D-2 で決定 |
| 再認証 | 役割の割当、閲覧者リストの変更、データ出力、支援アクセスの承認、セキュリティ設定の変更は、直近10分以内の多要素認証を求める |
| 総当たり対策 | アカウントの長時間ロックは行わず（他人による締め出しを防ぐ）、失敗回数に応じた待ち時間の延長と、IP 単位の回数制限を行う |
| セッション | アクセストークンの有効期間は短く（15分以内）、**API はリクエストごとに利用者の状態・退職日・失効記録（`user_session_revocations`）を確認**する（確認結果は最大60秒キャッシュ）。無操作での自動ログアウト（既定30分、施設設定）、最長時間（施設設定）。共用端末の扱いは D-2 |
| 退職・停止 | 退職日の翌日0時（施設のタイムゾーン）以降はログイン不可（退職日当日は利用可）。リクエスト時の確認と定期処理の二重で判定。**即時停止**（懲戒・紛失時）は管理者の操作で直ちに失効 |
| CSRF・XSS 等 | フレームワークの標準対策、CSP（読み込み元の制限。画像も自ドメインのみ）、入力検証、出力の自動エスケープ |
| 法人・施設の分離 | API層での判定＋DB の RLS（`database-design.md` 第2章）。RLS が無効なテーブルを CI で検出。分離テストを CI で必須化 |
| アクセス権限 | 操作×範囲の権限判定（`permission-design.md`）。四半期の権限棚卸し（最終ログイン日、長期未使用、管理権限者の一覧）。**90日使われていない管理権限を持つアカウントは自動停止**（ただし施設の最後の施設長は停止せず、施設と当社に警告）、その他は棚卸しで警告 |
| 操作ログ | 作成・更新・削除・承認・出力・権限変更・機密データの閲覧・AI 実行・ログインを記録。追記のみ（DB 権限で更新・削除不可）。法人ごと・日ごとのダイジェストを別アカウントへ複製し、改ざん・欠落を検出 |
| バックアップ | DB：日次＋時点復元（本番14日、実証期は最低7日）、加えて**別アカウント・国内・書換え不可の保管領域**への日次バックアップ（保守用DB利用者による）。ファイル：別アカウントの版管理付き保管領域へ日次複製（`database-design.md` 第8章） |
| 復旧目標（実証期、仮） | 復旧時間（RTO）24時間以内、失ってよいデータ量（RPO）24時間以内（時点復元が有効なら実際は数分） |
| データエクスポート | 法人・施設単位で CSV＋ファイル一式。`data.export` 権限者のみ、再認証・記録あり |
| データ削除 | 解約時：出力の提供 → 契約で定めた期間経過後に削除 → 削除証明（範囲は第7章の保存期間表と再委託先一覧に沿う）。バックアップは保持期間経過で消去されることを説明 |
| 秘密情報 | 本番の秘密情報はホスティングの秘密情報管理に保存し、**承認者付きの保護された配置環境（main ブランチからの配置のみ）**からしか読めない。コード・ログに出さない。CI で混入を検査 |
| 環境の分離 | 本番・検証・開発で DB・ストレージ・キーを完全に分離。本番データを他の環境に複製しない（復元訓練は本番と同じ統制の一時的な復元先で行い、確認後に破棄） |

### 3.2 インフラと当社側のアカウント（アプリの外の経路）

アプリ内で「当社は施設の承認なしに閲覧しない」としても、ホスティングの管理画面、DB所有者の認証情報、RLS を迂回する管理キー、環境変数、バックアップからは全データに届く。これらを次のように統制する。

| 対象 | 統制 |
|---|---|
| 対象アカウント | ホスティング（アプリ・DB・ストレージ）、GitHub、AI 事業者、エラー監視、メール配信、DNS、ドメイン |
| 多要素認証 | 全員必須（可能な限りフィッシングに強い方式：パスキー・セキュリティキー） |
| 人数 | 本番に触れられる人は最小限（実証期は2名以内を目標）。一覧を管理 |
| 管理キー | RLS を迂回する管理キー（例：Supabase の service_role キー）は**アプリで使わない**。DB への直接の公開窓口（例：Supabase の Data API）は無効化する（製品仕様は要確認） |
| DB の直接操作 | 原則禁止。必要時は「2名承認・時間制限・作業記録・事後に施設へ報告」（緊急手順） |
| 棚卸し | 四半期ごとにアカウント・権限・キーを確認 |
| 退職・異動 | 当日に権限を削除し、共有していた鍵・キーを入れ替える |
| リポジトリ | 本番の秘密情報を使う CI は、介護SaaS専用のリポジトリ（Q1）でのみ動かす。**専用リポジトリへの移行を PHASE 2 の開始条件にする** |

### 3.3 ファイル

| 項目 | 対策 |
|---|---|
| 受け付ける形式 | PDF、Word、Excel、JPEG、PNG。最大25MB（既定）。マクロ付き形式（.docm/.xlsm 等）は拒否。拡張子と中身の一致を確認 |
| 二段階の保管 | 受領は**隔離領域**へ。ウイルス検査と位置情報の除去を経て**保管領域**へ移し、隔離領域の原本は削除（受領時のハッシュ値だけ残す）。検査完了まで閲覧不可 |
| ウイルス検査 | 検査の実行場所（国内の検査用コンテナ、または検査サービス）を TD-030 で決定。外部サービスを使う場合は再委託先一覧に加える |
| 位置情報 | 画像の撮影場所（位置情報）を既定で除去。Office・PDF の作成者名等は証拠としての同一性を保つため変更しない（職員の氏名は C2） |
| 配信 | 期限付き（5分）のダウンロード URL。ファイルはアプリとは別のドメインから配信し、`Content-Disposition: attachment`（プレビュー以外）と `X-Content-Type-Options: nosniff` を付ける。ダウンロードを記録 |

### 3.4 ログ・監視・メールへの個人情報の混入防止

| 対象 | 対策 |
|---|---|
| アプリのログ | 個人情報（氏名、本文、ファイル名）を出さない。ID のみ。**個人情報が出ていないことを自動テストで確認** |
| エラー監視 | 個人情報の自動送信を無効（例：Sentry の `sendDefaultPii: false`）、画面録画（リプレイ）無効、リクエスト本文・クエリの除去 |
| ホスティングのログ | URL に個人情報を含めない（ID のみ）。保存期間を確認し、必要なログは国内の長期保存先へ転送 |
| メール | 本文は「新しい依頼があります」等とリンクのみ。業務名・氏名・ファイル名を書かない |

## 4. AI に関するデータ保護

| 項目 | 方針 |
|---|---|
| 送信フィルタ | AI 事業者へ出る**すべての内容**（最初の入力、検索ツールの結果、再送する会話履歴）を共通の送信フィルタに通す。フィルタは①データ区分で許可されていない項目の除去、②職員氏名の仮名化、③送信内容の記録を行う |
| 仮名化 | 職員氏名を「職員A」等の仮名に置換し、**仮名の対応は会話ごとに振り直す**（会話をまたいで同一人物を紐付けられないようにする）。回答表示時に復元 |
| 仮名化の限界 | 自由記述（質問文、議事録、書類本文）の中の入居者名・家族名・あだ名は確実には見つけられない。質問欄に「入居者の氏名を入力しないでください」と表示し、C4 の可能性がある本文は送らない（第2章）。少人数の施設では部署・役職の組合せで個人が分かることもあるため、仮名化後も**個人データとして扱う** |
| 記録 | 送ったレコードの種類とID、データ区分、置換件数を `ai_runs` に記録（漏えい時に「誰の情報を送ったか」を特定するため） |
| 事業者の条件 | データ保持期間、学習利用の有無、処理地域、ゼロデータ保持の可否、契約条件を**再委託先一覧**（`subprocessors.md`）で管理し、管理者画面に表示。年1回以上再確認 |
| 停止 | 施設設定で AI 機能を用途ごと・全体で無効化できる。AI なしで全業務が可能 |
| プロンプトインジェクション（書類などに仕込んだ指示文で AI を操ること） | ①AI に操作権限を与えない（読み取り専用の検索のみ、質問者の権限で実行）、②検索結果・書類本文は「信頼できないデータ」として区切って渡す、③**AI の回答では外部の画像・リンクを表示しない**（情報の外部送信を防ぐ。CSP でも制限）、④提案カードは内容を全文表示して人が確認、⑤AI 評価に注入・情報流出のテストを含める |

## 5. 外国事業者への個人データの提供・委託

前版の「データを国内リージョンに置くので問題ない」という書き方は誤りだった。データの保存場所が国内でも、**事業者が外国にある場合**は別途の整理が必要になる（個人情報保護法28条「外国にある第三者への提供」、個人情報保護委員会 Q&A 7-53「クラウドサービスの利用」、Q&A 10-25 など。解釈は要専門家確認）。

| 論点 | 内容 | 対応 |
|---|---|---|
| ホスティング（例：Vercel、Supabase） | 事業者が個人データを取り扱わない契約と適切なアクセス制御があれば「提供」に当たらない場合がある（Q&A 7-53）。当たらない場合も、施設は**外国の名称等を公表**する必要がある場合がある（Q&A 10-25） | 再委託先一覧で、契約条項・所在国・データ所在を整理し、専門家が判断 |
| AI 事業者 | 入力を処理して応答を返すため、上の例外に当たらないと考えるのが自然（要確認）。仮名化しても個人データのままと考えられる | 職員氏名を送らない設計を基本とし、それでも残る情報の扱いを専門家と確認。国内で処理できる提供経路（クラウド事業者経由の国内リージョン等）の有無を確認（要確認） |
| エラー監視・メール配信 | ログ・宛先・本文に個人情報が含まれうる | 第3.4節で混入を防いだうえで、再委託先一覧に記載 |
| 施設への支援 | 施設が行う公表・職員への説明 | 公表文と職員向け説明の雛形を用意（PHASE 5 の開始条件） |

## 6. 漏えい等への対応

法令上の骨格（個人情報保護法26条、同施行規則7〜9条、個人情報保護委員会の通則編ガイドライン。**詳細と最新の改正は要専門家確認**）：

| 項目 | 内容 |
|---|---|
| 報告対象（例） | 要配慮個人情報の漏えい等（1件でも対象）、財産的被害のおそれ、**不正の目的によるおそれ（不正アクセス等）**、1,000人超 |
| 期限 | 速報：知った後速やかに（概ね3〜5日以内）、確報：30日以内（不正の目的によるおそれは60日以内） |
| 委託先（当社）の義務 | 委託元（施設）に通知すれば、当社自身の委員会への報告義務は免れる（26条1項ただし書き） |

当社の基準（契約に明記する案）：

| 段階 | 期限 | 内容 |
|---|---|---|
| 第一報 | 疑いを認知してから**24時間以内** | 施設へ：発生の可能性、影響範囲の見込み、当面の措置 |
| 中間報告 | 72時間以内 | 判明事項（報告事項の項目に沿う：対象データ、人数、原因、二次被害のおそれ、再発防止策） |
| 確報の支援 | 施設の確報期限に間に合うよう | 調査結果の提供 |

- 証拠保全：ホスティングのログは保存期間が短い可能性があるため、アクセスログ・操作履歴を**国内の長期保存先へ常時転送**する
- 他施設のデータが見えた事案は、人数にかかわらず「不正の目的」等に当たる可能性を含めて直ちに専門家に相談
- 年1回、机上訓練を行う

## 7. 保存期間（案。専門家・施設と確認して確定）

| データ | 保存期間（案） | 削除方法 | 状態 |
|---|---|---|---|
| 業務・承認・提出の記録 | 契約期間中＋解約後の返却期間 | 解約時に削除 | 要決定 |
| 書類 | カテゴリの保存期限（施設が根拠付きで設定） | 期限到来で通知 → 人が削除 | 施設が決定 |
| 提出物（C2〜C3） | 依頼ごとに設定（既定：締切から1年） | 期限到来で通知 → 人が削除 | 要決定 |
| 操作履歴 | 5年以上を検討（2省ガイドラインの例示。法定保存年限との関係は要確認） | 期間経過後、変更内容の個人情報を要約に置換 | 要決定（TD-022） |
| ログイン履歴 | 操作履歴と同じ | 同上 | 要決定 |
| AI の会話・出力 | 1年（案） | 自動削除 | 要決定 |
| 退職者の職員台帳 | 退職後の一定期間（案：5年） | 個人を特定する項目を消去 | 要決定 |
| 利用記録（効果測定用） | 2年（案） | 自動削除 | 要決定 |
| アプリ・アクセスログ | 1年以上（転送先） | 自動削除 | 要決定 |
| バックアップ | DB 時点復元：本番14日（実証期は最低7日）、別アカウントのバックアップ90日（案） | 自動消去 | 要決定 |
| 外部事業者側（AI・監視・メール） | 再委託先一覧の各社条件 | 各社の条件に従う | 一覧で管理 |

## 8. 脅威と対策（主なもの）

| 脅威 | 対策 |
|---|---|
| 他施設のデータ閲覧（ID の書き換え） | RLS＋権限判定＋404 応答＋分離テスト（API・DB・ファイル・定期処理） |
| 施設管理者による権限の拡大 | 割当の規則（自分への割当禁止、自分の権限の範囲内、割り当てられる人の表）＋通知 |
| 当社スタッフ・管理アカウントからの閲覧 | 第3.2節のインフラ統制 |
| 退職者のアクセス | リクエストごとの状態確認＋失効記録＋定期処理 |
| 共用PC・共用タブレット | 無操作タイムアウト、共用端末モード（D-2） |
| 提出物の誤閲覧 | 書類と分離し、本人と確認者のみ閲覧 |
| 管理者アカウントの乗っ取り | 多要素認証必須、再認証、ログイン通知 |
| AI による誤情報・情報流出 | 根拠照合、送信フィルタ、外部画像・リンクの非表示、人の承認 |
| ファイル経由の攻撃 | 二段階の保管・検査・別ドメイン配信 |
| ランサムウェア・アカウント乗っ取りによるデータ消失 | 別アカウントの書換え不可バックアップ |
| マイグレーション事故 | 検証環境で事前実行、適用前のバックアップ、後方互換な段階変更 |

## 10. 契約に盛り込む事項（専門家の確認を前提とした項目リスト）
