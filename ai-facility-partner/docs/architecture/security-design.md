# セキュリティ・個人情報保護設計

> 法令・行政ガイドライン・契約上の要件は、**専門家（弁護士・情報セキュリティ専門家）の確認を前提**とする。本書は開発側の設計案であり、適合を保証するものではない。

## 2. 取り扱うデータの区分

| 区分 | 例 | MVP での扱い | AIへの送信 |
|---|---|---|---|
| C0 公開・一般 | 業務名、カテゴリ、委員会名 | 保存 | 可 |
| C1 業務情報 | 業務説明、期限、議事録本文、書類のテキスト | 保存 | 用途ごとに許可したもののみ |
| C2 職員の個人情報 | 職員氏名、部署、役職、ログインID | 保存（最小限） | **仮名に置き換えて送信**【仮定 Q4】 |
| C3 職員の機密情報 | 連絡先、資格証画像、評価 | MVP では原則保存しない（必要性確認後） | 不可 |
| C4 要配慮個人情報 | 入居者の病歴・介護情報、職員の健康情報 | **MVP に持ち込まない** | 不可 |

書類ファイルには入居者情報が含まれる可能性があるため、運用ルール（入居者の個人情報を含む書類はアップロードしない、または匿名化する）を施設と合意する。AI読み取り（PHASE 4）前に再評価。

## 3. 対策一覧

| 分類 | 対策 |
|---|---|
| 通信の暗号化 | HTTPS のみ（TLS 1.2 以上）、HSTS。DB・ストレージとの通信も TLS |
| 保存データの暗号化 | DB・ストレージ・バックアップをサービス側で暗号化（AES-256）。特に機密な列は将来アプリ側暗号化を追加 |
| データの所在 | DB・ファイル・バックアップは国内リージョン【仮定 Q2】 |
| パスワード | 認証サービスで管理（安全なハッシュ化）。最小12文字、漏えいパスワードの拒否、失敗回数によるロック |
| 多要素認証 | 構造は最初から対応。管理職以上は必須を推奨、職員は施設設定で選択 |
| セッション | HttpOnly・Secure・SameSite Cookie。無操作30分（設定可）で失効、最長12時間。退職・停止で即時失効 |
| CSRF・XSS 等 | フレームワークの標準対策、CSP（読み込み元の制限）、入力検証（Zod）、出力の自動エスケープ |
| 法人・施設の分離 | API層での自動付与＋DBの RLS。分離テストを CI で必須化 |
| アクセス権限 | 操作×範囲の権限判定（`permission-design.md`）。定期的な権限の棚卸し機能 |
| ファイル | 許可形式（PDF、Word、Excel、JPEG、PNG）・最大サイズ（既定25MB）の制限、拡張子と中身の一致確認、マクロ付き形式の拒否、ウイルス検査（完了まで取得不可）、非公開保管、期限付き（5分）ダウンロードURL、ダウンロードの記録。スマホで撮影した画像の**位置情報（撮影場所）は既定で除去**し、受領時と保存時のハッシュ値を両方記録（TD-024） |
| 操作ログ | 作成・更新・削除・承認・出力・権限変更・機密データの閲覧・AI実行を記録。追記のみ、改変不可 |
| ログイン履歴 | 成功・失敗・ロック・MFA 利用を記録。不審なログイン（新しい端末・多数の失敗）を管理者に通知 |
| バックアップ | 日次＋時点復元。四半期ごとの復元訓練 |
| 復旧手順 | `development/operation-guide.md` に記載。目標：復旧時間（RTO）24時間以内、失ってよいデータ量（RPO）24時間以内（実証期、仮） |
| データエクスポート | 法人・施設単位で CSV＋ファイル一式。出力は `data.export` 権限者のみ、記録あり |
| データ削除 | 解約時：出力の提供 → 保存期間（契約で定める）経過後に削除 → 削除証明。バックアップは保持期間経過で自動消去 |
| 保存期間 | 書類カテゴリ別の保存期限（施設が設定、根拠を記録）。期限到来時は通知し、人が確認してから削除 |
| 秘密情報 | APIキー等はホスティングの秘密情報管理に保存。コード・ログに出さない。秘密情報の混入をCIで検査 |
| 環境の分離 | 本番・検証・開発でDB・ストレージ・APIキーを完全に分離。**本番データを開発・検証に複製しない**。開発は架空データのみ |
| 当社のアクセス | SYSTEM_ADMIN は施設データを通常閲覧不可。障害対応時は施設長の承認＋期限付き＋全操作記録 |
| 依存部品 | 自動更新の通知、脆弱性スキャン（CI）、ロックファイルで版固定 |
| 監視 | エラー監視、異常なアクセス量の検知。ログには個人情報を出さない（マスキング） |

## 4. AI に関するデータ保護

| 項目 | 方針 |
|---|---|
| 送信の最小化 | 用途ごとに送信可能なデータ区分を定義（`ai_use_cases.allowed_data_classes`）。それ以外は送信前に除去 |
| 仮名化 | 職員氏名は「職員#12」のような仮名に置き換えて送信し、回答表示時に復元。**限界**：議事録や書類の本文など自由に書かれた文章では、登録済みの職員名は置換できるが、入居者名・家族名・あだ名などは確実には見つけられない。そのため、本文を AI に送る機能（議事録下書き、書類の読み取り）は PHASE 4 で施設の運用ルール（入居者情報を含めない等）と合わせて有効化の可否を判断し、施設設定で機能ごとに無効化できるようにする |
| 記録 | 送信したデータ区分・トークン数・費用を `ai_runs` に記録 |
| 事業者の条件 | データ保持期間、学習利用の有無、処理地域、ゼロデータ保持の可否、契約条件を `ai_vendor_terms` に記録し、管理者画面で表示。**確認日と確認者を記録し、年1回以上再確認** |
| 停止 | 施設設定で AI 機能を完全に無効化できる。AI なしで全業務が可能 |
| プロンプトインジェクション | 文書内の文章はデータとして扱い、AI に操作権限を与えない。AI 出力は提案として保存 |

## 5. 脅威と対策（主なもの）

| 脅威 | 対策 |
|---|---|
| 他施設のデータ閲覧（ID の書き換え） | RLS＋権限判定＋404 応答＋分離テスト |
| 退職者のログイン | 職員の退職処理でユーザー停止・セッション失効を同時実行 |
| 共用PCでのログインしっぱなし | 無操作タイムアウト、ログアウトの分かりやすい配置 |
| 提出物の誤送信・誤閲覧 | 提出物は本人と確認者のみ閲覧。ダウンロード記録 |
| 管理者アカウントの乗っ取り | 管理職以上の MFA、ログイン通知 |
| AI による誤情報 | 根拠照合、AI 出力の明示、人の承認 |
| マイグレーション事故 | 検証環境で事前実行、適用前のバックアップ、後方互換な段階変更 |

## 6. 実データ投入前のチェック（PHASE 5 の開始条件）

1. ガイドライン等から作成したチェックリストの全項目確認（専門家の確認を含む）
2. 施設との契約（利用規約、個人情報の取扱い（委託）、秘密保持、障害時の責任範囲）
3. 必須テスト12項目の合格
4. 外部の脆弱性診断（推奨）
5. 復元訓練の実施
6. AI事業者の条件確認と施設への説明
